# 行政書士分野 ブラッシュアップ計画

作成日: 2026-08-04。初版構築（用語905語・過去問200問・表示ページ一式）の完成後、品質を次段階へ引き上げるための改善計画。
ご指定の2軸に沿って改善案を整理する:

1. **Workflow（並列ファンアウト生成＋敵対的検証＋統合）**
2. **ループエンジニアリング**（タイマーは使わない）と、それに包含される **プロンプト / コンテキスト / ハーネス** 各エンジニアリング

---

## 0. 現状の弱点（`validate.py` による実測・2026-08-04）

初版は「量」の目標は達成したが、以下の**測定可能な品質欠陥**がある。感覚ではなく検証ハーネスの出力に基づく。

| 弱点                     | 実測値                                                    | 影響                                                          |
| ------------------------ | --------------------------------------------------------- | ------------------------------------------------------------- |
| **正解位置の偏り** | 正解=1 が**62%（125/200）**、**正解=5 は0件** | 「1を選べば当たる」学習を誘発。演習の実効性を損なう最大の欠陥 |
| **難易度の未分散** | 全200問が「標準」                                         | 基本固め／応用演習の出し分けができない                        |
| **出題形式の不足** | **5肢択一のみ**。多肢選択式・記述式が未収録         | 本試験（記述60点・多肢24点）の配点3割弱をカバーできていない   |
| 正確性の未検証           | 生成のみで第三者検証なし                                  | 誤答肢・条文引用・法改正反映の誤りが潜在                      |
| 難関論点の網羅           | 目安到達で打ち切り                                        | 頻出判例・横断論点の深掘り余地                                |

> これらは `docs/validate.py` を実行すると WARN として自動検出される（正解位置偏在・正解5が0・難易度単一）。改善のゴールは **この3警告を解消し、正確性を第三者検証で担保すること**。

## 1. 提案A — Workflow による「並列生成＋敵対的検証＋統合」

### 1-1. なぜ Workflow か

初版は `/loop` による**直列**生成だった。校閲・追加生成は科目間で独立しており、**並列ファンアウト**に向く。さらに生成物の正確性は「別の視点で反証させる」ことで初めて担保できる。これは1エージェントの自己申告では代替できない。

### 1-2. 設計（実体: `docs/workflows/verify-enrich-gyosei.workflow.js`）

```
Phase 1 Verify（科目×6を並列）
  各科目JSONを読み、全設問を校閲 → 指摘リスト(findings)を構造化出力
    観点: ①唯一の正解か ②誤答肢の質 ③条文/判例の実在・一致 ④2024-25改正の反映 ⑤曖昧/重複
        ↓ pipeline（バリアなし・科目ごとに独立して次段へ）
Phase 2 Adversarial（指摘ごとに独立スケプティック×2で反証）
  「少しでも疑わしければ real=false に倒す」→ 過半数が real の指摘だけ confirmedFixes に残す
        ↓
Phase 3 Enrich（科目×6を並列）
  ・rebalance: 選択肢を並べ替え正解位置を1〜5へ均等化（文言・正誤は不変、順序のみ）
  ・difficulty: 基本/標準/応用を付与
  ・newItems: 記述式1問（40字・模範解答付き）＋多肢選択式1問を新規生成
        ↓
戻り値 { confirmedFixes, enrich }（＝“案”）
```

### 1-3. 統合フロー（生成物を無検証で書き換えない）

Workflow は**案**を返すだけ。確定は main ループが決定論的ゲートを通して行う:

```
workflow 実行 → 案を受領
  → JSON へ反映（id をキーに冪等更新。rebalance は順序入替のみ・answer整合を再計算）
  → python3 docs/validate.py（エラー0 かつ 正解位置警告が解消するまで）
  → questions.js 再生成（LOOP_TASK §3-2 のスクリプト）
  → 差分をコミット（行政書士分野のみをスコープ）
```

### 1-4. 期待効果

- **速度**: 直列50イテレーション → 校閲・改善が6並列×数段で完了。
- **正確性**: 敵対的多数決により「もっともらしいが誤り」の混入を抑止。
- **形式網羅**: 記述式・多肢選択式を追加し本試験の配点構成に接近。

### 1-5. 実行方法

```
Workflow({ scriptPath: "shikaku/gyosei/docs/workflows/verify-enrich-gyosei.workflow.js" })
```

※ Workflow は多数のエージェントを起動しトークン消費が大きい。実行はユーザーの明示的な指示（オプトイン）があるときのみ。

## 2. 提案B — ループ／各エンジニアリング分野を生かした改善

タイマー（日次issue対応等）は不要なので使わない。ループの本質＝**「状態を外置きし、終了条件まで反復・自己修正する規律」**を、下位のプロンプト/コンテキスト/ハーネス各分野に落とし込む。

### 2-1. ループエンジニアリング（タイマー無し）

初版の弱点は「目安件数に達したら打ち切り」で、**未知の欠陥が残っても止まる**点だった。次の反復構造を導入する:

- **loop-until-dry（誤り枯渇まで反復）**: verify→fix を、**2ラウンド連続で確定指摘が0件**になるまで繰り返す。単純な「N周回して終わり」ではテール（残存誤り）を取りこぼす。
- **loop-until-metric（指標充足まで）**: `validate.py` の正解位置警告が消えるまで rebalance を反復。「件数」でなく**品質指標**を終了条件にする。
- **completeness critic（網羅性の批評役）**: 「未収録の頻出論点・未カバーの出題形式・未検証の主張はないか」を問う批評エージェントを1体置き、その指摘を次ラウンドの作業リストにする。
- **状態の外置き継続**: `PROGRESS.md` に加え、検証結果を `docs/verify-report.json` に蓄積し、ラウンド間で「既知の誤り」を重複処理しない（seen 管理）。

### 2-2. プロンプトエンジニアリング

初版の作問プロンプトは暗黙知に依存していた。明文化して品質を底上げする:

- **構造化出力（schema）を必須化**: 生成・検証とも JSON Schema で強制し、パースエラーや欠損項目をモデル側リトライで吸収（workflow の schema 参照）。
- **良問ルーブリックの明示**: 「誤答肢は“明確に誤り”かつ“紛らわしい”／正解位置は分散／1問1論点／条文番号を明記」を採点基準として渡す。
- **少数事例（few-shot）**: 既存の良問2〜3問を模範例として提示し、様式・粒度を揃える。
- **反証志向のプロンプト**: 検証役には「肯定」でなく「**反証せよ・疑わしきは不合格**」と指示（自己確証バイアスの抑制）。
- **一次情報の裏取り強制**: 「条文・判例名を自分の知識で確認し、断定できないものは『要一次情報確認』と明記」を全生成に付す（推測での断定を禁止）。

### 2-3. コンテキストエンジニアリング

各エージェントに「必要十分」な文脈だけを渡し、事故と重複を防ぐ:

- **担当科目のみを注入**: 校閲・生成エージェントには当該科目JSONだけを読ませ、他科目のノイズを排除（コンテキスト最小化 → 精度と速度の両立）。
- **既存項目の供給で重複回避**: 用語追加時は当該科目の既存 term 一覧を渡し、`議院不信任` 等の重複を生成前に抑止（初版では事後ガードが `議院内閣制` 重複を検知した — これを事前化する）。
- **一次情報の抜粋を retrieval**: 行政手続法・行政不服審査法・会社法等の条文抜粋や、試験研究センターの最新情報を文脈に添付し、記憶依存を減らす。
- **共有台帳をコンテキスト源に**: `PROGRESS.md` / `verify-report.json` を各ラウンド冒頭で読み、状態を私の記憶でなくファイルから復元（コンテキスト圧縮に耐える）。

### 2-4. ハーネスエンジニアリング

オーケストレーションの足場を決定論的に固める（生成AIの非決定性を機械で受け止める）:

- **検証ゲート `docs/validate.py`（作成済み）**: パース・answer範囲・choices数・id/用語重複・subject表記・questions.js整合を機械チェック。加えて**正解位置偏在・正解位置0件・難易度単一を品質警告**として検出。コミット前フック/CIに組み込み、**不合格ならコミットさせない**。
- **冪等な適用**: 修正・追加は `id` をキーに upsert。ワークフロー再実行や部分適用でも壊れない。
- **決定論的処理はコードで**: 重複排除・並べ替え・questions.js 統合は**エージェントでなく Python**で行う（LLM に数え上げ・整列をさせない）。
- **パイプライン設計**: 科目間はバリア不要なので `pipeline`（科目Aの検証中に科目Bを先へ）。全件横断の dedup 等、真に全成果が必要な箇所だけ `parallel`（バリア）にする。
- **スコープ限定コミット**: 反映は行政書士分野のファイルのみをステージ（初版反映時に他WIPの混入を patch 単位で除外した実績を手順化）。

## 5. 注意（初版の反省を引き継ぐ）

- 正確性を第一とし、一次情報で裏取りできない断定を避ける（グローバル方針）。
